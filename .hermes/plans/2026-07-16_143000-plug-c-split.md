# plug.c Split Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Status: revised 2026-07-26 after the plan's original premise was falsified.**
Read the reality check before doing anything. The task list below is still
valid; the goal, the ordering rationale, and every line number are not what the
first version said.

---

## Reality check (2026-07-26)

| | Plan was written | 2026-07-17 checkpoint | Today |
| --- | --- | --- | --- |
| `src/plug.c` | 7,148 lines | 6,479 | **8,682** |
| top-level functions | 184 | — | 197 static + 26 plug API |
| C tests | — | 175 | **327** |
| Python tests | — | 79 | **137** |
| `PLUG_STATE_VERSION` | — | — | **33** |

**`plug.c` grew by 2,200 lines while it was being split.** Extraction removed
about 670 lines; features added roughly 2,900. Reactivity routing, timeline
zoom/pan, lyric lane manipulation, caption typography, the caption face
browser, and the font import job all landed in `plug.c` because that is where
the composition root lives and no rule said otherwise.

**The line-count goal was the wrong target and should be dropped.** "Reduce
plug.c to 1,500-2,000 lines" is not achievable by extraction alone while
features arrive faster, and chasing it would mean either freezing the product
or extracting for the metric rather than for the seam. Both are worse than a
big composition root.

**What actually worked is not what this plan measured.** The genuine win of the
last ten days was *pure-logic* extraction into raylib-free, headlessly tested
modules:

`caption_layout` · `workspace_layout` · `timeline_layout` ·
`lyrics_editor_layout` · `ui_row_typography` · `ui_contrast` · `timeline_view` ·
`lyric_lane_edit` · `route_editor_state` · `scene_cadence_timing` ·
`font_catalogue` · `font_import_state` · `track_identity` · `preset_store`

None of these are in the original plan. Together they are why the C suite went
from 175 tests to 327, and why defects that were previously invisible — a
timeline strip disagreeing with itself, a lane drag the scrubber swallowed, a
caption ceiling baked in pixels, a panel that refused to draw at the minimum
window — became describable and testable. That pattern is the thing to keep
doing. Moving 400 lines of raylib drawing from one file to another is worth far
less and should be sequenced accordingly.

**Revised goal.** Not a line count. Two things:

1. **Get the four remaining stateful domains out of the composition root**, so
   `plug.c` stops being the place where assist, project, render, and scene-UI
   state can silently entangle. Ordered by tangle, not by size.
2. **Stop the regrowth**, with the rule in "Keeping it from growing back".

## Resolved open questions

The first version left these open. They are settled; do not re-litigate.

- **Should `Track` move to `track.h`?** The original recommendation was *no*.
  That was wrong and was reversed during Phase 2.4. `src/track.h` exists and is
  the reason modules can take `Track *` directly instead of needing vtables.
- **`notice_push` as a bottleneck dependency?** Settled by the services-struct
  pattern: `Lyric_Editor_Services` passes `notice_push`, `mark_project_dirty`,
  `font()`, `active_button_id`, and an optional `Font_Browser_Services`. Copy
  that shape for every new module; it keeps the module raylib-light and lets
  tests pass stubs.
- **`djb2` dual use?** Resolved; it is shared, not duplicated.

## Critical constraints (read before any task)

Unchanged in substance from the original, with corrections:

1. **Hot reload is the hard boundary.** `plug_pre_reload`/`plug_post_reload`
   hand the entire `Plug` state between the old and new `.so`/DLL. Extracted
   module state must live inside `Plug` and be passed as a pointer, or be added
   to the handoff with a state-version bump. Prefer the former. The handoff
   code, `state_magic`, and `state_version` stay in plug.c.
   **New trap, found 2026-07-26:** `plug_pre_reload` sizes its owned-allocation
   inventory with an exact literal (`5 + p->tracks.count`). Adding a heap
   pointer to `Plug` without bumping that literal overruns the array. Any
   extraction that moves a heap-owning field must check it.
2. **Build registration.** Every new engine `.c` goes in `append_engine_sources`
   in `src_build/nob_stage2.c`. Add to `append_tested_core_sources` **only** if
   the module is genuinely headless — the test binary links `-lm` and nothing
   else, so anything behind a raylib call is unreachable from the C suite.
3. **Style.** Four-space indent, same-line braces, `snake_case`, module-prefixed
   public symbols. No `-ffast-math`; keep finite checks.
4. **No behaviour change.** Preview/export determinism, provenance lanes,
   transactional writes, close guards, and the two network boundaries are
   product invariants. A "refactor" that changes one is a bug.
5. **Commit per task, and keep each one reviewable.**

## Validation rhythm (run after every task)

```sh
./nob build debug 2>&1 | tail -3      # clean, zero new warnings
./nob test debug 2>&1 | tail -2       # at least 327
```

Before the merge gate: `./nob build release|sanitize|hotreload`,
`./nob test release|sanitize`, `python3 -m unittest discover -s tests/adapters`
(at least 137), `./nob dist`, and — because these tasks touch render and
project code — a short real render plus `ffprobe`, and a byte-identical 720p
canary if drawn pixels could have moved.

Where a task touches a panel, capture it: `tools/ui_fixture.sh` then
`tools/ui_capture.sh build/ui-review/after`, and compare against a run from
before the change. A layout regression is invisible to every other suite.

## Recommended order

Dependency-correct, and cheapest-risk-first within that:

**1.2 (finish notices) → 2.5 (font import) → 1.3 (transport) → 2.2 (project)
→ 2.3 (render) → 1.4 (scene UI) → 2.6 (lyrics panes) → 2.1 (assist)**

Rationale, which differs from the original:

- **1.2 first** because it is half-finished and small; leaving a domain split
  across two files is worse than either home.
- **2.5 early** because it is the newest, best-understood code, its pure logic
  is already extracted, and it is the cleanest rehearsal of the services
  pattern on a module with a child process.
- **2.2 before 2.3** because render publication and project publication share
  the transactional-write discipline, and doing project first means render
  copies a settled pattern.
- **2.1 last**, still. Assist depends on the lyrics editor, notices, project
  dirty-marking, and now the lyric-reference row. It should sit on stable
  modules rather than defining a bridge the others invalidate.

## Task detail (changed tasks only)

The original bodies for 1.1-2.4 remain accurate in *shape*. What follows are
the corrections and the two new tasks.

### Task 1.2 — finish the notice extraction

Move `notice_severity_color`, `draw_notice_wrapped_text`, `notice_tray`
(plug.c:6603-6744) into `ui_notice.c`. `notice_tray` is called from three sites
in `plug.c`; keep the call sites. `ui_notice.c` is deliberately **not** in the
tested-core list once it draws — that is the precedent, do not "fix" it.

### Task 1.3 — transport, with one authority already in place

`timeline` is 396 lines at plug.c:2811. Since the plan was written,
`timeline_view.c` became the only seconds↔pixels mapping for the strip, so the
extracted module consumes that rather than doing its own arithmetic.
`lyric_editor_ui_draw_lane` is already a module call from inside `timeline`;
keep it that way.

**Watch out:** the strip owns a press for a whole gesture and must release
`active_button_id` unconditionally on mouse-up. `lyric_editor_ui_release_lane_claim`
exists precisely because a stranded claim freezes every button in the
application. Do not restructure the press/release ownership while moving it.

### Task 1.4 — scene UI, now including the route editor

Add `scene_route_editor_panel` (plug.c:5643, 226 lines) to the function list.
Its pure logic already lives in `route_editor_state.c`, so the extraction is
drawing plus wiring.

### Task 2.2 — project workflow, now including asset bundling

Add to the function list: `bundle_project_asset` and the font/licence bundling
inside `save_project_to_path`. `build_project` now takes stored paths for
audio, ASCII image, font, and licence.

**Watch out:** the bundle-before-publish ordering is pinned by
`test_productization.py::test_project_save_bundles_every_asset_source_before_publication`,
which also asserts there is exactly **one** call each to
`musi_project_bundle_asset` and `musi_project_reference_published_asset` in the
whole file. Moving them keeps that true; splitting them does not.

### Task 2.5 — extract the caption face import → `src/font_import.c` (new)

**Objective:** Move the font job's process handling and service implementations
out of the composition root. ~479 lines.

**Functions:** `find_font_helper`, `font_helper_available`, `font_job_set_status`,
`font_job_fail`, `font_job_read_artifact`, `font_job_start`,
`font_job_finish_catalogue`, `font_job_finish_fetch`, `font_job_cancel`,
`poll_font_job`, and the `font_service_*` implementations behind
`font_browser_services`.

**Already extracted, do not touch:** `font_catalogue.c` (bounded TSV readers)
and `font_import_state.c` (consent, deadlines, panel choice, nonce fencing).
This task moves only the glue.

**State:** `Plug` currently holds `font_catalogue` (heap), `font_catalogue_loaded`,
`font_network_allowed`, `font_job`, `font_job_state`, `font_job_nonce`,
`font_job_started_at`, `font_job_finished_at`, `font_process`, and four path
buffers. They become a `Font_Import_Context` embedded in `Plug`.

**Watch out:**
- `font_catalogue` is a heap pointer in the reload inventory. See Constraint 1's
  new trap.
- `caption_imported_font_load`/`_unload` rasterize into `Plug` and are called
  from `plug_update`; they are caption glue, not import glue. **Leave them in
  plug.c** with the other font handles.
- Consent is per run and deliberately not persisted. Moving it must not make it
  survive a restart.
- The digest re-verification in `font_job_finish_fetch` is the security
  boundary. Move it verbatim.

**Commit:** `refactor: extract the caption face import job from plug.c`

### Task 2.6 — split `lyrics_editor_ui.c` (new)

**Objective:** It is 1,425 lines and now hosts three whole-panel panes — the cue
editor, the caption style form, and the caption face browser — which are never
shown at once and share almost nothing but the panel rectangle.

**Suggested split:** `caption_style_ui.c` (style form + swatch/slider helpers)
and `font_browser_ui.c` (browser + consent panel), leaving the cue editor, the
lane, and import/export in `lyrics_editor_ui.c`.

**Watch out:** all three panes share `Lyric_Editor` state and the pane toggles.
Keep the toggle logic and the `style_pane`/`font_pane` flags in one place; the
guard that a pane switch goes through `lyric_editor_ui_allow_context_change` is
a close-guard invariant.

**Do this after 2.1 or skip it** if the panes stop growing. It is hygiene, not a
tangle.

## Keeping it from growing back

The extraction lost a race it was never told it was running. The rule that
would have prevented it, now in `AGENTS.md`:

> Keep reusable logic out of `plug.c` when it can be expressed as a small
> dependency-light module with headless tests.

Make it operational:

1. **A new feature's pure logic starts in its own module, before the UI.** Every
   feature this month that did this — routing, zoom, lane editing, font import —
   produced tests that caught real defects before anything was drawn. Every one
   that did not, grew `plug.c`.
2. **A value-only header must not include `<raylib.h>`.** `ui_palette.h` and
   `scene_settings_values.h` exist for this; the raylib header wraps the
   raylib-free one so tests can read the single source of truth.
3. **New `plug.c` code should be composition:** wiring modules, owning `Plug`,
   handing out services. If a new function in `plug.c` has logic worth a test,
   it is in the wrong file.
4. **Do not re-target a line count.** Track instead: how many domains still keep
   state in `Plug` that only they read. Today: assist, project, render, scene
   UI, font import, transport. That number should only fall.

`MUSIALIZER_PLUG` API and wrappers; the `Plug` struct; `load_assets`/
`unload_assets` including every `Font` handle and `caption_imported_font_load`;
`plug_init`/`plug_update`/`plug_shutdown`; the whole reload handoff; track
ingestion (`plug_load_track`, `plug_load_ascii_image`); the audio callback and
analyzer glue; `scene_render`/`make_scene_frame`/`draw_scene_lyric_overlay`/
`caption_measure_raylib`; `current_track`, `notice_push`, `mark_project_dirty`,
`scene_seed_for_track`; `plug_apply_ui_probe`; and `preview_screen`, which is
the composition root's layout and *should* know about every panel.

A realistic floor is **3,000-3,500 lines**, not 1,500-2,000.

## Risks

- **Reload state leakage** is still #1. Mitigate with Constraint 1, the
  allocation-inventory check, and `./nob build hotreload` once per phase.
- **Windows-only assist code** cannot be runtime-tested here. Static review
  only; say so in the commit, per the `PRODUCT_READINESS` precedent.
- **Layout regressions are invisible to every test suite.** Capture the panel
  before and after. A defect you cannot photograph is one nobody reviews.
- **Extraction competing with features again.** If a feature lands mid-phase,
  finish the current task and re-measure rather than racing it.
