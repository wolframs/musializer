# plug.c Split Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Reduce `src/plug.c` from 7,148 lines / 184 functions to a thin orchestration core by extracting cohesive modules, following the codebase's existing precedent (`ui_notice.c`, `scene_switch.c`, `track_timeline.c`, `editor_draft.c`).

**Architecture:** `plug.c` keeps the `MUSIALIZER_PLUG` API surface, the global `Plug *p` state, assets, the main update loop, and hot-reload handoff. Everything else moves into small modules that receive explicit context pointers (never a hidden second global). The public plug API is untouched; this is a pure internal refactor.

**Tech Stack:** C11, raylib, `nob` build system. No new dependencies.

**Branch:** `refactor/plug-c-split` (created, at master `9dddd46`).

## Revised extraction approach for Phase 2 (post-`track.h`)

Each extracted module now:
1. `#include "track.h"` and takes `Track *` / `Tracks *` parameters directly.
2. Receives a small pointer to its slice of `Plug` state (embedded struct, so
   hot reload memcpy still works — Constraint 1 unchanged).
3. plug.c keeps thin `static` wrappers so existing call sites are untouched.

The `notice_push`/`mark_project_dirty`/`current_track` helpers should move
into a small shared module (or stay as thin plug.c wrappers the modules call)
— decide when 2.4 lands; prefer a `editor_services` home if three modules all
need them.

## Critical constraints (read before any task)

1. **Hot reload is the hard boundary.** `plug_pre_reload`/`plug_post_reload` (plug.c:6925-7070) hand the entire `Plug` state between the old and new `.so`/DLL. A module extracted with its own `static` file-scope state **will be lost on reload**. Rule: extracted module state must either (a) live inside the existing `Plug` struct and be passed as a pointer, or (b) be explicitly added to `Plug_Reload_Handoff_V1` with a state-version bump and round-trip test. Prefer (a). The reload handoff code itself and `state_magic`/`state_version` handling **stay in plug.c**.
2. **Build registration.** Every new engine `.c` must be added to `append_engine_sources` in `src_build/nob_stage2.c` (~line 88). Only add to `append_tested_core_sources` if the module is genuinely headless (no raylib draw calls) — `ui_notice.c` is *not* in the tested list because it draws; that is the precedent for UI modules. Audit POSIX/Windows splits, not just Linux.
3. **Style.** Four-space indent, same-line braces, `snake_case`, module-prefixed public symbols (`assist_job_start`, not `start`). No `-ffast-math`, keep finite checks.
4. **No behavior change.** Preview/export determinism, provenance lanes, transactional writes, close-guards are all product invariants. If a "refactor" changes any of them, it's a bug.
5. **Do not commit** to master; all work stays on `refactor/plug-c-split`. Commit after every task.

## Risks / open questions

- **Reload state leakage** is the #1 risk — mitigated by Constraint 1 + smoke-run after each phase (hot-reload build: `./nob build hotreload` once per phase to at least compile the host/plug split).
- **`djb2` dual use** (widgets + assist) — resolve in 1.1 by making it shared, don't duplicate it.
- **Windows-only assist code** can't be runtime-tested here — static review only, say so in commits (PRODUCT_READINESS precedent).
- **Open question:** should `Track` move to a `track.h`? It would decouple modules further but touches everything; recommend **no** for this pass — keep structs in plug.c, pass pointers.
- **Open question:** `notice_push` used by nearly every module — if it becomes a bottleneck dependency, give each extracted context a `Ui_Notice_Stack *` (or whatever `ui_notice.h` exposes) rather than a callback. Decide in Task 1.2.
